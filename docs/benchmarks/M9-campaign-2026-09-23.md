## M9b round 1 — what was found and fixed

Baseline (`M9-baseline-2026-09-23.md`) had every pipelined GET/SET row at
0.38–0.49×. Diagnosis (syscall-counting probe `note/syscall-probe`, CPU +
alloc profiles in `profiles/`):

1. **The baseline matrix's fixed key was the artifact.** Without `-r`,
   redis-benchmark sends every command to one key → one shard goroutine →
   a serialized ping-pong: each command did a full `DoTok` round trip
   (conn goroutine → shard queue → shard goroutine → done channel →
   scheduler wakeup), two goroutine switches per command. The fixed-key
   CPU profile was 52% scheduler churn (`findRunnable`/`usleep`/
   `pthread_cond_wait`) with most cores idle. With `-r 1000000` Ultima
   already beat Redis (1.2×) — shard parallelism works.
2. **Even replying `+OK` without touching the engine capped at ~1.9M
   ops/s** — the per-command handoff was nearly free when spread across
   shards; the cost only bit when serialized onto one shard.

Fixes landed (all semantics-preserving; full suite + differential green):

- **Burst coalescing** (`lib/commands/burst.go`, `lib/respserver`): the
  RESP front-end now passes the whole pipelined read burst to
  `Engine.ExecuteBurst`, which runs maximal segments of whitelisted
  single-key commands (audited `e.do`-only handlers: strings family +
  single-key expiry/probe commands) as per-shard group tasks submitted
  asynchronously (`shard.DoTokAsync`), with `do()` executing inline via a
  per-shard slot on ConnState. A 16-command burst costs one parallel
  round of handoffs instead of sixteen serial ones. Disabled (safe
  fallback to per-command) with maxmemory configured (OOM gate's
  `EvictNow` fans out to all shards — would self-deadlock inline) and
  inside MULTI (queue appends would race).
- **DoTok cheapening** (`lib/shard`): pooled buffered completion
  channels; shard run/park loops now send instead of close.
- **AOF capture check-only mode** (`lib/commands/aof.go`): with
  appendonly off, `rewriteForPersist` no longer clones argv (was ~0.9 GB
  per 6 s of SET load, pure waste); the save-rule dirty count is kept
  exact via a nil-argv `LogCommand` (guard in `lib/persist/manager.go`).
- **Reader marks scratch** (`lib/resp`): the `*` parse loop reuses a
  per-Reader marks slice instead of allocating 128 B per command.
- **ExecuteBurst scratch**: segment groups/out/dones buffers reused per
  connection.
- Reverted: skipping `trackAccess` when maxmemory==0 — broke tested
  behavior (keys written before maxmemory is set must be eviction
  victims; `lib/commands/oom_test.go`). Would need a tracker warm-up on
  the 0→N transition; deferred.

Results vs baseline (medians above): fixed-key GET 0.43×→**0.88×**,
fixed-key SET 0.44×→**0.58×**, random-key SET/GET **1.05–1.37×** (new
rows; 4-client probing shows GET-random ~1.6×). PING unchanged (0.80–
0.99×), P1 rows unchanged (~0.66× — inherent per-command round trip).

Where the remaining time goes (for M9c): fixed-key SET is latency-bound
on the burst round trip (~2 scheduler wakeups vs Redis's zero), not CPU
— cores idle at ~3/14 during the fixed-SET profile. The random-key
aggregate caps ~1.4–1.8M ops/s at the front-end/scheduler layer (echo
ceiling measured 2.36M with 4 driver processes); closing that means
front-end alloc/copy work (per-command `cmd.Raw` copy ~103 B, per-SET
key string + Entry + value-copy allocations — GC assist time lands on
the allocating conn goroutine) and possibly deeper pipelining of the
burst fan-out. 4-client drivers: single redis-benchmark processes cap
~1–1.9M ops/s themselves; gate runs need parallel drivers (or memtier —
not yet on PATH despite install attempt).
