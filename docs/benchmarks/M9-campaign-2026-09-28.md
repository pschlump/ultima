## Part 1 — -c200 profiling pass (fixed-key SET, the regression row)

Profiles: `docs/benchmarks/profiles/2026-09-28-m9c/`
(`cpu-c200-fixedset.pprof`, `goroutine-c200.txt`, `mutex-c200.pprof`,
`block-c200.pprof`, `trace-c200.out`, `shards-under-load.json`), captured
under `redis-benchmark -c 200 -P 16 -t set -d 64` on a single fixed key.

Findings:

1. **The server is latency-bound, not CPU-bound.** CPU profile total is
   311% of ~1400% available — ~11 of 14 cores idle. Top CPU consumers are
   scheduler machinery: `runtime.usleep` 24.3%, `runtime.kevent` 16.5%,
   `runtime.pthread_cond_signal` 14.6% — a goroutine park/wake storm, not
   command execution.
2. **Block profile: 75% of all block time is connection goroutines parked
   in `execSegment`'s `<-done`** (`lib/commands/burst.go`), i.e. waiting
   for the single owning shard to drain their burst. 25% is shard
   goroutines idle in their queue select (the other 63 shards have no
   work — fixed key = one shard does everything).
3. **The shard queue IS the serializer — and the fixed
   `ShardStat.QueueDepth` now sees it.** Under load the owning shard's
   queue held 194 pending tasks (sampled via `/api/v1/shards`; every other
   shard 0). Throughput on the fixed-key rows is therefore bounded by the
   single shard goroutine's serial drain rate — the same structural limit
   as Redis's one thread, plus our handoff wake cost per burst.
4. **Mutex profile: app mutexes are NOT the bottleneck at -c200.** Total
   mutex delay ~0.8 s over 10 s wall, dominated by runtime internals
   (`findRunnable`). Neither `latencyTable.mu` nor `cs.metaMu` registers.
   → the Part-2 bookkeeping-mutex fixes are **deprioritized by evidence**
   (revisit only if random-key/multi-shard profiles disagree).
5. **`trackAccess` (eviction LRU/LFU bookkeeping) runs even with
   maxmemory=0**: 6.3% of total CPU on the SET path
   (`lru.Put` + `lfu.Touch` + map churn), all on the one hot shard
   goroutine. This is the M9b-deferred skip (broke `oom_test.go` on the
   0→N transition). Largest single app-level CPU item → fix #1.
6. GC is ~10% of CPU (mallocgc + scan + sweep) — allocation reduction on
   the SET/argv path remains worthwhile but secondary.

Consequences for Part 2, in priority order:

- **Fix 1: skip `trackAccess` when maxmemory==0** (with tracker warm-up
  on the 0→N config transition). Direct profile evidence.
- **Fix 2: burst round-trip overlap** — 75% block time is the submit→done
  ping-pong. Investigate letting the connection goroutine parse ahead
  while the shard executes, preserving per-connection command order
  (submission order per shard is FIFO; cross-shard reordering is NOT
  acceptable — per-connection sequential semantics are Redis-exact).
- **Bookkeeping-mutex work (slowlog stripe, metaMu copy, time.Now
  collapse): deprioritized** — no mutex-profile evidence at -c200.
- The 4× gate on **fixed-key** rows requires one shard goroutine to
  sustain 4× Redis's single-thread rate (~7.6M ops/s) including handoff
  — not reachable under the owner-goroutine model (§4.3); expected
  outcome is parity-class on fixed-key rows and the 4× push concentrated
  on multi-shard rows (random-key, where the front-end ~1.8M ops/s
  aggregate cap is the next wall). Will be reported per the plan's
  honesty clause with these profiles as evidence.

## Fix log

(fixes land below with before/after numbers, one entry each)

### Fix 1 — skip `trackAccess` when maxmemory==0 (2026-09-28)

`lib/shard/shard.go` (`trackAccess` early-return on `maxMemory.Load() <= 0`)
+ lazy LRU warm-up in `maybeEvict` on the 0→N transition (`trackWarm`
flag, `warmEvictTrackers` seeds the LRU trackers from the keyspace; LFU
needs no seed — untracked = counter 0 = coldest). Lazy design chosen over
eager fan-out in `SetMaxMemory` so CONFIG SET maxmemory inside MULTI/EXEC
(under PauseAll) cannot deadlock. The M9b `oom_test.go` failure mode
(allkeys-lru finds no victims after runtime maxmemory enable) is covered
by warm-up; `TestEvictionPolicyReprieve` and the whole OOM suite pass.

A/B on the same machine, same binary flags, median of 3 × `-n 300000
-P 16 -d 64` fixed-key rows (Ultima only, req/s):

| Row | Before | After | Delta |
|---|---|---|---|
| SET -c 50 | 1,063,829 | 1,485,148 | +39.6% |
| GET -c 50 | 1,807,229 | 1,829,268 | +1.2% (noise) |
| SET -c 200 | 996,677 | 1,382,488 | +38.7% |
| GET -c 200 | 1,630,434 | 1,734,104 | +6.4% |

vs the 2026-09-23 campaign Redis numbers (SET -d64 -c50 1,785,714 /
GET 2,083,333): fixed-key SET ratio 0.58× → ~0.83×. The eviction tracker
work was ~40% of the single hot shard's execution budget — consistent
with the profile (trackAccess 6.3% of TOTAL CPU across ~3.1 cores busy ≈
20% of the one core that matters).

Full `go test ./lib/shard/... ./lib/commands/...` green.

### Fix 2 — redcon: eliminate the per-command `cmd.Raw` copy (2026-09-28)

`lib/resp/redcon.go` readCommands: alias the read buffer instead of
copying ~103 B + 1 malloc per command (42% of front-end alloc_space under
pipelined random-key load). Retention audit for the aliasing invariant
(every command of a read batch is consumed before the next refill):
MULTI queue (cloneArgs), WATCH/waiters (string()), stored values
(dupBytes), pub/sub channels (string()), **PUBLISH payload — fixed with
dupBytes in cmdPublish** (broker frames escape to async push queues),
**MONITOR hello events — fixed with cloneArgs** (async monitor streams);
AOF records serialize synchronously in `appendSeq` (no retention).

A/B vs the fix-1 binary (same rows as fix 1 + random-key -r 1M -c200):
**throughput-neutral within noise** on every row (fixed SET c50 ~1.47M,
random SET c200 ~1.46M vs 1.51M before, GET-random ~1.68M vs 1.60M).
Kept as GC hygiene: it removes ~7.6 GB/10 s of garbage (42% of
alloc_space), which matters once the real ceiling moves. Lesson recorded:
the random-key rows are NOT allocation-bound at current throughput.

Full suite + race + `tests/` green.

### Fix 3 — pub/sub: byte-capped queues + batched flushes (2026-09-28)

Two-part change:

1. **`lib/pushq` + config** (M9c plan): the fixed 4096-message push queues
   in all three front-ends (RESP/WS/gRPC, three hardcoded `pushQueueCap`
   constants) replaced by a shared growable, byte-capped queue behind
   `server.pubsub_client_buffer_mb` (default 32 MB — Redis's
   `client-output-buffer-limit pubsub 32mb` hard-limit default). Overflow
   → connection teardown (slow consumer), semantics preserved per
   front-end; QUIT close-after-pending ordering preserved via zero-cost
   control markers.
2. **Batched push flushes**: the RESP push writer drained its queue with
   one `PushValue` per message — render + flush + write syscall + writeMu
   per message per subscriber. Now drains up to `pushBatchMax` (1024)
   queued frames and flushes once via the new fork method
   `resp.Conn.PushValues` (one writeMu acquisition, one flush).
   Pre-existing deadlock fixed en route: `conn.Close()` flushes under
   writeMu, so a publisher goroutine tripping the overflow could block
   forever behind a push writer itself blocked on a dead client's socket
   — the race predates the batching (batching made it reproducible).
   Slow-consumer teardown now uses the new fork method
   `resp.Conn.CloseHard` (socket close, no flush). WS/gRPC teardowns are
   not affected (no write-mutex in their close paths).

`bin/bench-pubsub.sh` before → after (8 subscribers, PUBLISH -c 50):

| Leg | Before (4096 cap, per-msg flush) | After | Redis 7.2.7 |
|---|---|---|---|
| -P 16 | 36K/s (0.05×) | **315K/s (0.40×)** | 792K/s |
| -P 1 | 28K/s (0.20×) | 59K/s (0.41×) | 144K/s |
| -c 1 -P 1 | 15K/s (1.68×) | 15K/s (1.68×) | 9K/s |

**Survivors/delivery (the plan's pub/sub test gate): 8/8 subscribers up
with exact full delivery (min=300000) on every leg, before AND after** —
the byte cap alone achieved that; batching then lifted throughput 8.7×.

The ≥1× secondary target is NOT met (0.40× on multi-publisher legs).
Evidence gathered: subscriber-count sweep on the -P16 leg — 1 sub
1.65M/s, 2: 1.46M, 4: 1.23M, 5: 708K, 6: 475K, 7: 374K, 8: 325K.
Aggregate deliveries peak ~4.9M msg/s at 4 subscribers and fall to ~2.6M
at 8. CPU profile (`cpu-pubsub-fanout.pprof`): 71% of CPU inside
`Writer.Flush` (blocked socket writes), 75% in write syscalls — the
fleet-wide budget (server's goroutine model ~5 cores + 8 driver
processes + the benchmark) is the ceiling: Redis's 1-core server leaves
~13 cores for the drivers, ours does not. bufio 4KB→64KB and batch
128→1024 were tried and are throughput-neutral (kept: no downside).
Further gains need a structurally cheaper delivery path (per-subscriber
CPU), not more buffering. Recorded as secondary-target miss per the
plan's honesty clause; the gating delivery assertions pass.

`lib/pushq` unit tests, parameterized respserver/wssrv boundary tests,
race + integration suites all green.

### Diagnostic — random-key rows are driver-capped (2026-09-28)

Random-key -c200 CPU profile (`cpu-c200-randomset.pprof`): 54% of CPU is
`syscall.rawsyscalln`, and 42.6s of the 60.2s is `write(2)` — server
goroutines blocked writing to clients that are not draining. That is the
signature of a saturated driver, not a saturated server. Direct test
(SET -d 64 -r 1M, two -c200 -P16 drivers vs one): 1.51M ops/s single →
876K + 862K = **1.74M aggregate with two drivers** (+15%). The
BENCH_DRIVERS knob (Part 0) is validated as necessary for gate runs; the
sweep (Part 4) will establish how far aggregate scales (3/4-driver legs
pending).

Notes:

- Two drivers lift BOTH servers (Redis fixed SET 1.79M→1.97M, PING mbulk
  2.44M→2.97M, and -P1 rows 220K→304K/s — the old single-driver -P1
  numbers were driver-capped too; the -P1 ratio dip is measurement
  correction, not a server regression: Ultima's -P1 absolute rate rose
  137K→172K/s).
- The **-c50→-c200 regression is gone**: with the new -c100/-c400 sweep
  rows the curve is flat (GET 0.96–1.04×, SET 0.65–0.76× across
  c50→c400). M9b coalescing + fix 1 removed it.
- Harness hardening note: DRIVERS>1 + the -c400 rows exhausts macOS's
  ~16K ephemeral ports via TIME_WAIT ("Can't assign requested address");
  `rps()` now retries a rep with 15 s backoff (one retry absorbed it on
  the gate run) and reports driver stderr on failure.
- **The 4× gate is NOT met on any row** (best 1.62×). Per the plan's
  honesty clause: recorded with profiles. The remaining gap is
  architectural, as diagnosed in Part 1: fixed-key rows are bounded by
  one shard goroutine's serial drain rate (parity-class with Redis's
  single thread — we are at 0.74–1.04×, up from 0.40–0.45× at campaign
  start); multi-shard rows are bounded by per-connection front-end CPU
  (parse/submit/write per command across 200 goroutines) at ~1.6–2.7M
  ops/s aggregate vs Redis's ~1.2–3.0M single-thread — the 4× target
  needs ~5–8M ops/s of front-end headroom that the current
  goroutine-per-connection + channel-handoff model does not have. Any
  further step changes the settled dispatch model (§4.1/§4.3) and must
  go through an explicit §15 amendment.
