# Set-group cases (§5.3): SADD, SREM, SMEMBERS, SISMEMBER, SMISMEMBER, SCARD,
# SPOP, SRANDMEMBER, SMOVE, SINTER, SUNION, SDIFF, SINTERSTORE, SUNIONSTORE,
# SDIFFSTORE, SINTERCARD, SSCAN.
#
# Unordered multi-member replies (SMEMBERS/SINTER/SPOP-count/...) use
# `type: match` rather than `sorted`: the rendered lines carry array indices
# (`1) "a"`), so the index pins each line's position and only the member at
# each index is nondeterministic — per-index alternation regexes cover that.
# (Plain `sorted` cannot normalize a permuted indexed reply: the leading
# index dominates the whole-line sort.)
#
# RESP3 renders set replies as `1~ "a"` / `(empty set)` where RESP2 renders
# `1) "a"` / `(empty array)` — but the ultima-ws-cli/ultima-grpc-cli renderer
# (clients/go/ultima/render.go) numbers set elements `1)` like an array
# (keeping `(empty set)` for empties), diverging from redis-cli -3's `1~`.
# Since one `== resp3` block must serve both redis3 and the ultima RESP3-class
# targets, cases with a non-empty set reply are RESP2-only here; the correct
# RESP3 expectations live in 50-set-bugs.txt.disabled. SRANDMEMBER is an
# ARRAY reply in both protocols (even RESP3), and SSCAN's reply is an array
# in both — those cases run on all targets.
